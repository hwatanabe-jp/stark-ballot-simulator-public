# テストと形式検証

暗号の仕組みが正しくても、チェックの呼び忘れや画面の判定ミスによって票の欠落を見逃し、誤って Verified と表示する可能性があります。

実装の確認には、既知の失敗を再現するテスト、さまざまな入力を作って試すテスト、条件を満たす限り成り立つ性質を数学的に示すモデルを組み合わせています。

| 方法                   | 例                                                   | 得られる確認                                                 |
| ---------------------- | ---------------------------------------------------- | ------------------------------------------------------------ |
| 手書きのテスト         | 必須チェックを一つ失敗させる                         | その場合に成功表示にならない                                 |
| Property-based Testing | 票や Merkle ツリーの大きさ・順番を変えて多数生成する | 試した入力で仕様上の性質が崩れない                           |
| Lean による証明        | 最終判定を抽象モデルで定義する                       | そのモデルでは、完全成功なら必須チェックがすべて成功している |

各方法で確認できる範囲は異なります。手書きテストは経験した失敗を再現するケースを確実に残せます。生成テストは人が思い付かなかった組み合わせを探せます。Lean は抽象モデルの条件を証明できますが、そのモデルと実際の TypeScript・Rust が対応するかは、さらにテストで照合する必要があります。

重点的な検査対象は、証拠不足での成功表示と、秘密を含むファイルの配布です。これらは一つの関数だけでは決まらないため、[単体・結合・E2E テスト](unit-integration-e2e.md)で確認します。
