# 設計判断

この部では、STARK Ballot Simulator が PoC として意図的に割り切った点と、構築を通じて得た設計上の知見を記録します。
実装、運用、監査の前提を共有するために、制約の理由と影響範囲を明確にします。

## 判断の記録方針

各章は、目的に応じて記録軸を分けます。

| 章                 | 記録軸                               |
| ------------------ | ------------------------------------ |
| PoC の意図的な制約 | 制約の内容、受け入れた理由、影響範囲 |
| 設計ふりかえり     | 背景、知見、改善候補                 |

この部は、次の 2 章で構成します。

- **PoC の意図的な制約**：今は意図的に変えない割り切りを記録します。
  固定票数 64、ビットマップチャンク漏洩、非 GPU 前提のように、PoC スコープ内で受け入れた制約が対象です。
- **設計ふりかえり**：構築を通じて見えた構造課題（カテゴリ A）と、制約が見えた後に整理し直した設計判断（カテゴリ B）を記録します。
  改善候補は確定した移行計画ではなく、次に検討しうる選択肢として扱います。
  カテゴリの定義は [設計ふりかえり](design-retrospective.md) に集約しています。

## この部に含まれる章

## 想定読者と前提

- 想定読者：本システムを評価する監査者、採用検討者、実装の追従者
- 前提：本書の [暗号プロトコル](../protocol/index.md)、[zkVM 設計](../zkvm/index.md)、[検証パイプライン](../verification/index.md) を一読し、PoC のスコープ（[はじめに](../introduction.md) 参照）を把握していること

## 本章で扱わないもの

- 一般的な投票システムの脅威モデル比較
- 本番運用に向けた具体的な実装ロードマップ
- 採用判断のためのコスト試算や ROI 評価
